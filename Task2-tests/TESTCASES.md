# Тест-кейс E2E-001: Полный цикл работы с объявлением

## Эндпоинты
`POST /api/1/register` → `POST /api/1/autorize` → `POST /api/1/item` → `GET /api/1/item/{id}` → `DELETE /api/2/item/{id}`

## Сценарий
Полный цикл: регистрация, авторизация, создание, получение, удаление объявления.

## Предусловия
Нет.

## Шаги выполнения
1. Сгенерировать уникальный `username` (например, `user_{timestamp}`).
2. Отправить `POST /api/1/register` с телом `{username, password}`.
3. Сохранить `id` и `username` из ответа.
4. Отправить `POST /api/1/autorize` с телом `{username, password}`.
5. Сохранить `accessToken`.
6. Сгенерировать уникальное `name` объявления (например, `item_{timestamp}`).
7. Отправить `POST /api/1/item` с заголовком `Authorization: Bearer {accessToken}` и телом `{name, description, price, sellerID: <id из шага 3>}`.
8. Сохранить `itemId` из ответа.
9. Отправить `GET /api/1/item/{itemId}` с тем же токеном.
10. Отправить `DELETE /api/2/item/{itemId}` с тем же токеном.

## Ожидаемые результаты
1. **Register**: Статус 200 OK, тело ответа содержит `id` (integer) и `username` (string).
2. **Autorize**: Статус 200 OK, тело ответа содержит `accessToken` (string) и `tokenType: "Bearer"`.
3. **Create Item**: Статус 201 Created или 200 OK, тело ответа содержит `id`, `name`, `sellerID` (который должен совпадать с ID из токена).
4. **Get Item**: Статус 200 OK, тело ответа содержит данные созданного объявления (необходимо проверить `name`, `price`, `sellerID`).
5. **Delete Item**: Статус 200 OK или 204 No Content.
6. **Verify Delete**: Повторный запрос `GET /api/1/item/{itemId}` возвращает статус 404 Not Found.

## Примечания к тест-кейсам

### Генерация уникальных данных
Для работы на общем стенде использовать следующие форматы:
- **Username**: `user_{timestamp}` (например, `user_1704067200`) или `user_{UUID}` (например, `user_a1b2c3d4-e5f6-7890-g1h2-i3j4k5l6m7n8`)
- **Name объявления**: `item_{timestamp}` или `item_{UUID}`
- **Description**: Можно использовать статический текст, так как конфликты маловероятны

### Работа с токеном
- Токен извлекается из ответа `/api/1/autorize` из поля `accessToken`
- Заголовок авторизации: `Authorization: Bearer {accessToken}`
- ID пользователя можно получить:
  - Из ответа `/api/1/register` (поле `id`)
  - Декодировав JWT-токен (если используется JWT)
  - Через дополнительный эндпоинт профиля (если есть)

### Проверка соответствия sellerID
При создании объявления критически важно:
1. Получить свой `userId` при регистрации
2. Использовать **точно этот же** `sellerID` в теле запроса POST /api/1/item
3. Несовпадение приведёт к 403/400 ошибке

### Ожидаемые коды ответов
| Код | Значение | Когда ожидается |
|-----|----------|-----------------|
| 200 | OK | Успешный GET, DELETE |
| 201 | Created | Успешный POST (создание ресурса) |
| 204 | No Content | Успешный DELETE (без тела ответа) |
| 400 | Bad Request | Ошибка валидации (неверный формат, missing fields, граничные значения) |
| 401 | Unauthorized | Отсутствие токена, невалидный токен |
| 403 | Forbidden | Недостаточно прав (чужой sellerID, попытка удалить чужое) |
| 404 | Not Found | Ресурс не найден |
| 409 | Conflict | Конфликт (дубликат username) |

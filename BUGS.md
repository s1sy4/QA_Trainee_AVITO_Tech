# Отчёт о найденных дефектах тестового стенда (BUGS.md)

В ходе написания и прогона автотестов были выявлены следующие несоответствия поведения API ожидаемой бизнес-логике и стандартам безопасности.

---

## BUG-API-01: Отсутствие валидации отрицательной цены
**Эндпоинт:** `POST /api/1/item`  
**Серьёзность:** High (Высокая)  
**Связанный тест-кейс:** BV-002  

**Описание:**  
API успешно создаёт объявление, если в поле `price` передано отрицательное число. Сервер не проводит валидацию на положительность цены.

**Шаги воспроизведения:**
1. Авторизоваться и получить валидный Bearer-токен.
2. Отправить `POST /api/1/item` с телом, содержащим `"price": -100` (и остальные валидные поля).

**Ожидаемый результат:**  
Сервер возвращает `400 Bad Request` с сообщением о валидации (например, "Price must be positive").

**Фактический результат:**  
Сервер возвращает `200 OK`, объявление создаётся и сохраняется в базе данных с отрицательной ценой.

## BUG-API-02: Отсутствие ограничения на максимальное значение цены
**Эндпоинт:** `POST /api/1/item`  
**Серьёзность:** Medium (Средняя)  
**Связанный тест-кейс:** BV-004  

**Описание:**  
API принимает экстремально большие значения поля `price` (например, `9999999999999` и выше) без возврата ошибки валидации.

**Шаги воспроизведения:**
1. Авторизоваться и получить валидный Bearer-токен.
2. Отправить `POST /api/1/item` с телом, содержащим `"price": 9999999999999`.

**Ожидаемый результат:**  
Сервер возвращает `400 Bad Request` (превышение максимального лимита).

**Фактический результат:**  
Сервер возвращает `200 OK`, объявление создаётся.

## BUG-API-03: Некорректная обработка нулевых значений в объекте statistics (Falsy 0)
**Эндпоинт:** `POST /api/1/item`  
**Серьёзность:** High (Высокая)  
**Связанный тест-кейс:** Особенности валидации стенда  

**Описание:**  
Если в объекте `statistics` передать значение `0` для полей `likes`, `contacts` или `viewCount`, сервер возвращает ошибку валидации, считая поле отсутствующим. Вероятно, на бэкенде используется нестрогая проверка (например, `!value` вместо `value === undefined`), из-за чего `0` интерпретируется как `false`.

**Шаги воспроизведения:**
1. Отправить `POST /api/1/item` с телом, содержащим `"statistics": {"likes": 0, "contacts": 0, "viewCount": 0}`.

**Ожидаемый результат:**  
Сервер возвращает `200/201 OK`, так как `0` — это валидное числовое значение для статистики.

**Фактический результат:**  
Сервер возвращает `400 Bad Request` с ошибкой `"поле likes обязательно"`.

## BUG-API-04: Критическая уязвимость IDOR при удалении объявления (Horizontal Privilege Escalation)
**Эндпоинт:** `DELETE /api/2/item/{id}`  
**Серьёзность:** Critical (Критическая)  
**Связанный тест-кейс:** NEG-006  

**Описание:**  
Эндпоинт удаления объявления не проверяет права доступа. Любой авторизованный пользователь может удалить объявление, принадлежащее другому пользователю, просто зная его `itemId`. Сервер не сверяет `sellerId` объявления с `id` пользователя из Bearer-токена.

**Шаги воспроизведения:**
1. Пользователь A создаёт объявление (получает `itemId`).
2. Пользователь B авторизуется со своим токеном.
3. Пользователь B отправляет `DELETE /api/2/item/{itemId_A}`.

**Ожидаемый результат:**  
Сервер возвращает `403 Forbidden`, так как пользователь B не является владельцем ресурса.

**Фактический результат:**  
Сервер возвращает `200 OK` и успешно удаляет чужое объявление.

## BUG-API-05: Нестандартный формат ответа при создании ресурса (API Design Flaw)
**Эндпоинт:** `POST /api/1/item`  
**Серьёзность:** Medium (Средняя)  
**Связанный тест-кейс:** E2E-001, POS-003  

**Описание:**  
При успешном создании объявления сервер возвращает не стандартный JSON-объект с полями созданного ресурса (включая `id`), а текстовое сообщение, из которого приходится парсить UUID.

**Шаги воспроизведения:**
1. Отправить валидный `POST /api/1/item`.

**Ожидаемый результат:**  
Ответ в формате JSON: `{"id": "uuid-...", "name": "...", "price": ...}` со статусом `201 Created`.

**Фактический результат:**  
Ответ: `{"status": "Сохранили объявление - <uuid>"}` со статусом `200 OK`. Для получения ID требуется парсинг строки (`split(" - ")[1]`), что нарушает принципы RESTful API и усложняет интеграцию.

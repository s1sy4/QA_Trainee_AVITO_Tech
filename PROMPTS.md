## 1
**Цель:** Получить базовую таблицу, покрывающую основные позитивные и негативные сценарии, с соблюдением формата Markdown.  
**Использованный промпт:**

Доступные эндпоинты:

    POST /api/1/register (публичный, возвращает id, username)
    POST /api/1/autorize (публичный, возвращает accessToken, tokenType)
    POST /api/1/item (защищённый, требует Bearer token. ВАЖНО: sellerID в теле должен строго совпадать с id из токена)
    GET /api/1/item/{id} (защищённый)
    GET /api/1/{sellerID}/item (защищённый)
    GET /api/1/statistic/{id} и GET /api/2/statistic/{id} (защищённые)
    DELETE /api/2/item/{id} (защищённый)

Задача: Составь подробную таблицу тест-кейсов в формате Markdown.
Ограничения и требования к покрытию:

    Включи позитивный E2E-сценарий (Register -> Autorize -> Create Item -> Get Item -> Delete Item).
    Обязательно добавь негативные сценарии: запрос к защищённому эндпоинту без токена (ожидание 401), попытка создать объявление с чужим/несовпадающим sellerID (ожидание 403 или 400).
    Примени технику анализа граничных значений для поля price при создании объявления (например: 0, отрицательное число, максимально допустимое значение, нечисловое значение).
    В шагах или предусловиях явно указывай необходимость генерации уникальных данных (например, использование UUID или timestamp для username и name объявления) для избежания конфликтов на общем стенде.

Формат вывода: Таблица Markdown со следующими колонками: 
TC-ID | Категория | Эндпоинт | Название сценария | Предусловия | Шаги | Ожидаемый результат (HTTP-код + проверка тела ответа)

## 3
**Цель:** Сгенерировать основную массу автотестов (NEG, BV, SEC) на основе уже работающих E2E и POS-тестов, с учётом всех выявленных особенностей тестового стенда.  
**Использованный промпт:**  

Напиши автотесты для API Авито на pytest + allure.

Контекст:  
У меня есть фикстура `api_client` в conftest.py, которая регистрирует пользователя, авторизует его, предоставляет хелпер `create_item(payload)` и автоматически удаляет созданные объявления в teardown. Также есть `second_api_client` для тестов с двумя пользователями.

Пример моего рабочего теста (для понимания стиля):
```python
@allure.epic("API Tests")
@allure.feature("Positive Scenarios")
@allure.story("Get Item")
@allure.title("POS-004: Успешное получение объявления по ID")
def test_get_item_by_id_returns_200(self, api_client):
    item_name = f"item_{uuid.uuid4().hex[:8]}"
    payload = {
        "name": item_name,
        "price": 1000,
        "sellerId": int(api_client["user_id"]),
        "statistics": {"contacts": 1, "likes": 1, "viewCount": 1}
    }
    create_resp = api_client["create_item"](payload)
    assert create_resp.status_code in [200, 201]
    item_id = create_resp.json()["status"].split(" - ")[1]
    
    get_resp = api_client["session"].get(f"{BASE_URL}/1/item/{item_id}")
    assert get_resp.status_code == 200
    assert get_resp.json()[0]["name"] == item_name
```

Особенности API (уже проверены на практике):  
1. Поле `sellerId` — с маленькой `d`
2. `statistics` не принимает `0` — используй минимум `1`
3. ID объявления: `response.json()["status"].split(" - ")[1]`
4. `GET /api/1/item/{id}` возвращает массив → бери `json()[0]`
5. Эндпоинт статистики: `/api/1/statistic/{id}` (без `s`)

Что нужно написать:  
1. BV-001...BV-006 — параметризованный тест для граничных значений price (0, -1, 999999999, 9999999999999, "abc", null)
2. NEG-001, NEG-002 — доступ без токена / с невалидным токеном
3. NEG-003, NEG-004 — создание с чужим sellerId / без sellerId (параметризация)
4. SEC-002, SEC-003 — регистрация дубликата / неверный пароль

Требования:  
- Allure-декораторы: `@allure.epic`, `@allure.feature`, `@allure.story`, `@allure.title` с ID тест-кейса
- Шаги через `with allure.step(...)`
- Уникальные данные через `uuid.uuid4().hex[:8]`
- Имена функций: `test_[действие]_[условие]_[ожидаемый_код]`
- Для NEG-001/NEG-002 используй чистый `requests.Session()` без токена

**Использованный промпт:**

Пример моего рабочего теста:

```python
@allure.epic("API Tests")
@allure.feature("E2E")
@allure.title("E2E-001: Полный цикл")
def test_full_item_lifecycle(self, api_client):
    item_name = f"item_{uuid.uuid4().hex[:8]}"
    payload = {
        "name": item_name,
        "price": 5000,
        "sellerId": int(api_client["user_id"]),
        "statistics": {"contacts": 1, "likes": 1, "viewCount": 1}
    }
    create_resp = api_client["create_item"](payload)
    assert create_resp.status_code in [200, 201]
    item_id = create_resp.json()["status"].split(" - ")[1]
    
    get_resp = api_client["session"].get(f"{BASE_URL}/1/item/{item_id}")
    assert get_resp.status_code == 200
    assert get_resp.json()[0]["sellerId"] == api_client["user_id"]
```

Важные особенности API (уже проверены на практике):
- sellerId с маленькой d
- statistics не принимает 0, используй минимум 1
- ID объявления парсится из response.json()["status"].split(" - ")[1]

- Эндпоинт статистики: /api/1/statistic/{id} (без s на конце)

Нужно написать:
